# Writing your Laocoon policy

Laocoon sits between your application and its language model. It makes sure the assistant never does anything
the logged-in user could not do, and that nothing with side effects happens without the user's approval.
Everything it enforces comes from **one file you write: your policy**.

This guide walks through writing one for a small helpdesk application, then installing the database views it
produces. The complete reference for every key is [SPEC.md](SPEC.md), and [eclass.yaml](eclass.yaml) is a full
production example (Athena eClass, 30 tools).

**Who does what**

| Person | Task |
|---|---|
| Integration engineer | writes the policy (this guide, steps 1–9) |
| Security or data protection officer | reviews what the policy lets Laocoon read and do (steps 5–10) |
| Database administrator | reviews and runs the generated SQL script (step 11) |

---

## How it fits together

```
                          your policy (YAML)
              ┌──────────────────┴───────────────────┐
     the rules                              data_model
     tools, roles, approvals,               your tables and relations, and what
     references, data protection            each rule's constraint means in them
              │                                      │ generated by Laocoon
              │                                      ▼
              │                       SQL script: views + a read-only login
              │                                      │ reviewed and run by your DBA
              ▼                                      ▼
     Laocoon enforces the rules ──── reads only those views, live, for every check
```

The **rules** say who may call which tool on what. The **data model** says how to check a rule such as "the
ticket belongs to one of my teams" in your database. From the data model, Laocoon writes a script that creates one
small view per object kind and per relation, and a login that can read those views and nothing else.

On PostgreSQL the database itself enforces that limit: the login cannot read your tables, only the views. Your
DBA can see exactly what Laocoon reads, and revoke it at any time.

---

## Before you start

You need:
1. **The tools** your application declares to the model: their names and argument names, exactly as in the JSON
   schemas you send.
2. **The roles** your application assigns to users, and how it tells Laocoon who is logged in. Either it writes
   these lines into the system message it builds on the server:
   ```
   - User id: 42
   - Username: ana
   - Role: agent
   ```
   or it sends the signed identity header (recommended in production). Laocoon checks the system-message identity
   against your database.
3. **Your database schema:** which table holds each kind of object, and which columns link them.

**Where Laocoon gets its facts.** Choose one:

| Your situation | Option | You set up |
|---|---|---|
| your data is in PostgreSQL | **views** (this guide, steps 5–11): the database enforces what Laocoon may read | `data_model`, and a script your DBA runs |
| you have an authorization service, or your data is not in SQL (a document store, a graph, a directory, other services) | **AuthZEN**: Laocoon asks your policy decision point and never sees your data | an `authzen` mapping, and a PDP that speaks AuthZEN 1.0 ([below](#option-your-own-authorization-service-authzen)) |
| MySQL / MariaDB | views: the script is generated, but Laocoon's connection is not available yet | |
| SQLite | views, limited by Laocoon itself, or an exported file (step 11) | |
| no database access and no PDP | facts learned through your own read tools ([SPEC §10](SPEC.md#10-settings-for-the-no-database-mode-laocoon_authz_sourcelookup)) | |

Steps 1–4 and 7–10 are the same for every option.

## The example application

A helpdesk. Customers open tickets, and agents work in teams and handle their teams' tickets.

```
accounts(id, login, display_name, role, email, phone, password_hash)
teams(id, name)
team_members(team_id, account_id)
tickets(id, team_id, customer_id, assignee_id, is_closed, subject, body)
comments(id, ticket_id, author, body)
```

The application's tools: `list_my_tickets`, `get_ticket` (the ticket with its comments), `reply_ticket`,
`assign_ticket`, `get_user`, `delete_account` and `export_tickets`.

---

## Step 1: the skeleton

```yaml
version: 2
app: acme-helpdesk
default: deny
roles: [customer, agent, admin]
```

`default: deny` is the only option: a tool you do not list is never shown to the model, and a role you do not
grant cannot use it.

## Step 2: every tool, its effect, and who may call it

```yaml
tools:
  list_my_tickets: {effect: read,        allow: {customer: true}}
  get_ticket:      {effect: read,        allow: {customer: true, agent: true, admin: true}}   # narrowed in step 7
  reply_ticket:    {effect: communicate, allow: {customer: true, agent: true}}
  delete_account:  {effect: write,       allow: {admin: true}, locked: true}
  export_tickets:  {effect: external,    allow: {}}          # nobody: the model never sees it
```

`effect` matters: anything other than `read` is a side effect, and by default it waits for the user's approval
(step 8). `locked: true` makes that approval impossible to switch off, which is right for irreversible actions.

## Step 3: arguments that are the user

`list_my_tickets(customer_ref)` must always be the caller's own tickets. Do not trust the model to fill it in:

```yaml
  list_my_tickets:
    effect: read
    bind: {customer: [customer_ref]}
    allow: {customer: true}
```

Laocoon removes `customer_ref` from what the model sees, fills it in with the caller's id, and denies the call if
anything else is put there.

## Step 4: references

The model writes references the way people do: "ticket 12", "assign it to Bob". Declare which arguments are
references and to what:

```yaml
refs:
  ticket_id: ticket
  user_ref: user
  assignee_ref: user
  customer_ref: user
```

Laocoon resolves each one to an id **once**, before any check. The tool then runs with exactly the object that was
checked. A reference that matches nothing, or more than one object, is denied: "Bob" is never guessed between
two Bobs.

## Step 5: the objects (`data_model.objects`)

Now tell Laocoon where each kind of object lives and which harmless columns it may read: names, codes and state.

```yaml
data_model:
  principal: user
  objects:
    user:   {table: accounts, fields: {username: login, name: display_name, role: role},
             refs: [{username: exact, name: iexact}, {name: contains}], label: "{name} ({username})"}
    team:   {table: teams, fields: {name: name}, enum: name, refs: [{name: iexact}], label: "{name}"}
    ticket: {table: tickets, fields: {closed: is_closed}}
```

- `fields` maps the name used in the policy to your column. The user kind needs `username` and `role` (to check
  the identity) and may have `name`.
- `refs` says how a reference by name is found, tier by tier. For a user: the exact login or the full name in any
  case first, then part of the name. Each tier must give exactly one match.
- `label` is how the object appears on approval cards.
- `enum` lists the field Laocoon may offer the model as the user's allowed values, so the model does not guess.

**Leave personal data out.** `email`, `phone`, `subject` and `body` are not listed, so Laocoon cannot read them.
The studio rejects any column you list in `sensitive_fields` (step 9).

## Step 6: the relations

```yaml
  relations:
    team.member:     {table: team_members, from: team_id, to: account_id, target: user}
    user.teams:      {reverse: team.member}          # the same pairs, read from the user's side
    ticket.team:     {table: tickets, from: id, to: team_id, target: team}
    ticket.customer: {table: tickets, from: id, to: customer_id, target: user}
    ticket.assignee: {table: tickets, from: id, to: assignee_id, target: user}
```

A relation is a pair of columns:
- `from` holds the object's id;
- `to` holds the related object's id;
- `target` is the related object's kind.

The pair may sit in the object's own table (`tickets.customer_id`) or in a link table (`team_members`).

## Step 7: what the rules mean (`constraints`), and using them

A constraint is a **path**. It starts at the object the argument refers to, follows relations, and ends at the
logged-in user:

```yaml
  constraints:
    own_ticket:      ticket.customer               # the ticket's customer is me
    team_ticket:     ticket.team.member            # the ticket's team has me as a member
    assigned_ticket: ticket.assignee
    teammate:        user.teams.member             # that user is in one of my teams
    open:            not ticket.closed             # a path may end at a field; `not` negates it
```

Now narrow the tools with them:

```yaml
  get_ticket:
    effect: read
    allow:
      customer: {ticket_id: own_ticket}
      agent:    {ticket_id: "team_ticket|assigned_ticket"}     # any of
      admin:    true
  reply_ticket:
    effect: communicate
    allow:
      customer: {ticket_id: [own_ticket, open]}                # all of
      agent:    {ticket_id: [team_ticket, open]}
  assign_ticket:
    effect: write
    allow:
      agent: {ticket_id: team_ticket, assignee_ref: teammate}  # both arguments are checked
      admin: true
    locked: true
  get_user:
    effect: read
    allow: {agent: {user_ref: "self|teammate"}, admin: true}   # self is built in
```

> **Never use a `not` path alone.** It is true when nothing matches, and that includes a ticket that does not
> exist. That is why `open` only ever appears next to `own_ticket` or `team_ticket`.

Every check reads the database live: an agent who is removed from a team loses access to its tickets with the
next call.

## Step 8: approvals

The defaults are safe: reads run, and every side effect waits for an approval card that the user confirms. Change
them per role where it makes sense:

```yaml
approvals:
  roles:
    agent: {reply_ticket: false}       # agents reply without a card; customers still confirm theirs
```

The studio warns about every side effect that runs without approval for some role, so this one shows up as a
deliberate warning. Locked tools (`assign_ticket`, `delete_account`) always ask, whatever is written here.

## Step 9: data protection

```yaml
sensitive_fields: [password_hash, email, phone]     # masked in the audit log, never readable by the data model

private_data:                                       # values the model must never see
  classes:
    EMAIL: {pattern: '[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)*\.[A-Za-z]{2,}', fields: [email],
            normalise: casefold}
    PHONE: {fields: [phone], match: field}
    PASSWORD_HASH: {fields: [password_hash], action: drop}
```

With `private_data`, an e-mail address in a tool result reaches the model as `⟦EMAIL:k3x9qa⟧`. Laocoon puts it
back in the answer for the user, and into a tool argument only when its decision table allows it ([SPEC
§8](SPEC.md#8-private_data)).

Content other people wrote must be marked, so that the classifier checks it and a side effect proposed after
reading it waits for approval:

```yaml
  get_ticket:
    untrusted_output: {author_field: author, ref: comment}
```

## Step 10: validate in the studio

Open the policy in the studio: the **Policies** page of Laocoon's web console. It shows:
- every issue on its line: errors block saving, warnings and infos are for your attention;
- the **effective permissions** per tool and role: access, scope, approval.

For this policy it reports no errors and one warning (`reply_ticket` runs without approval for `agent`, as
intended). The matrix reads:

| Tool | customer | agent | admin |
|---|---|---|---|
| `list_my_tickets` | yes | — | — |
| `get_ticket` | own_ticket | team_ticket \| assigned_ticket | yes |
| `reply_ticket` | own_ticket + open, **asks** | team_ticket + open | — |
| `assign_ticket` | — | team_ticket, teammate, **asks (locked)** | **asks (locked)** |
| `get_user` | — | self \| teammate | yes |
| `delete_account` | — | — | **asks (locked)** |
| `export_tickets` | — | — | — |

Saving keeps a draft. The policy becomes live only when your Laocoon operator deploys it.

## Step 11: the database script

Laocoon generates the script from `data_model` (`laocoon.views sql --dialect postgres`; in a hosted deployment,
your operator sends it to you). For this policy it is, in one transaction:

```sql
CREATE SCHEMA IF NOT EXISTS "laocoon";

-- objects: ids, names, codes and state the rules use (no personal data beyond names)
CREATE VIEW "laocoon"."obj_user"   AS SELECT "id", "login" AS "username", "display_name" AS "name", "role" FROM "public"."accounts";
CREATE VIEW "laocoon"."obj_team"   AS SELECT "id", "name" FROM "public"."teams";
CREATE VIEW "laocoon"."obj_ticket" AS SELECT "id", "is_closed" AS "closed" FROM "public"."tickets";

-- relations: pairs of ids
CREATE VIEW "laocoon"."rel_team_member"     AS SELECT "team_id", "account_id" AS "member_id" FROM "public"."team_members";
CREATE VIEW "laocoon"."rel_ticket_team"     AS SELECT "id" AS "ticket_id", "team_id" FROM "public"."tickets";
CREATE VIEW "laocoon"."rel_ticket_customer" AS SELECT "id" AS "ticket_id", "customer_id" FROM "public"."tickets";
CREATE VIEW "laocoon"."rel_ticket_assignee" AS SELECT "id" AS "ticket_id", "assignee_id" FROM "public"."tickets";

-- the login (set its password separately: \password laocoon)
CREATE ROLE "laocoon" LOGIN;
ALTER ROLE "laocoon" SET default_transaction_read_only = on;
ALTER ROLE "laocoon" SET statement_timeout = '2s';
GRANT USAGE ON SCHEMA "laocoon" TO "laocoon";
GRANT SELECT ON "laocoon"."obj_user" TO "laocoon";
-- … one GRANT SELECT per view, by name
```

(Shortened. The real script also drops each view before recreating it, creates the role only if it is missing,
and revokes old grants first, so running it again is safe.)

### Review checklist for the DBA

- [ ] The script contains only:
  - `CREATE SCHEMA`, and `DROP VIEW` / `CREATE VIEW`;
  - a `DO` block that creates the role only if it is missing, and `ALTER ROLE`;
  - `REVOKE` and `GRANT`;
  - with `--functions`, also `CREATE FUNCTION … SECURITY DEFINER`.
- [ ] Every view reads **one** table, and only the columns listed. None of them holds personal data, unless you
      asked for the optional before-value views (`--previews`) and agreed to grant them.
- [ ] Every `GRANT` names a view in schema `laocoon`. Nothing is granted on your own schema.
- [ ] There is no password in the script.

After running it:

```sql
\password laocoon
\dp laocoon.*                                   -- exactly the views above, SELECT for laocoon
SELECT table_schema, table_name FROM information_schema.role_table_grants WHERE grantee = 'laocoon';
```

Then connect **as the login** and confirm it cannot read your data:

```bash
psql "dbname=helpdesk user=laocoon" -c "SELECT email FROM public.accounts"    # must fail: permission denied
psql "dbname=helpdesk user=laocoon" -c "SELECT * FROM laocoon.obj_user LIMIT 3" # works: ids, logins, names, roles
```

Laocoon's `views check` then confirms, view by view, that the login can read what the policy needs. To see
exactly what Laocoon reads over time, log the `laocoon` role's statements (`pgaudit`, or `log_statement` for that
role).

**SQLite.** There is nothing to grant. Laocoon opens your file read-only, creates these views in its own connection
only, and refuses any other read. That limit is Laocoon's own. For one your side enforces, run
`laocoon.views export --every 5`: it copies the views' rows into a separate file, which is all Laocoon gets.

## Step 12: go live

Your Laocoon operator deploys the policy with `LAOCOON_AUTHZ_SOURCE=views` and the login's connection string. The
console then shows the decisions, the approvals and the audit log.

## Option: your own authorization service (AuthZEN)

If you already run an authorization service, or your data is not in a SQL database, Laocoon can ask your **policy
decision point** (PDP) instead of reading any data. It speaks the OpenID **AuthZEN Authorization API 1.0**.
- Your rules (steps 2–4, 8–9) stay the same.
- Instead of `data_model`, you map each constraint to a question your PDP answers.
- Nothing is installed in your database, and Laocoon never sees your data, only "yes" or "no" and the lists your
  PDP returns.

```yaml
authzen:
  subject: user
  identity: {action: identity}               # your PDP confirms who is logged in (see below)
  resources:
    user:   {type: user, search: directory, refs: [{username: exact, name: iexact}, {name: contains}],
             label: "{name} ({username})"}
    ticket: {type: ticket, id: string, search: view}   # a document store: ids like 65f1c0a2e4b0d1
  constraints:                               # Laocoon's constraint → your PDP's action on that resource type
    own_ticket:      {resource: ticket, action: read_own}
    team_ticket:     {resource: ticket, action: work_on}
    assigned_ticket: {resource: ticket, action: assigned}
    teammate:        {resource: user,   action: teammate}
    open:            {resource: ticket, action: is_open}
```

Give every kind a `search` action if your PDP can answer it: it is how Laocoon checks that a ticket id exists.
Without one, an admin whose rule is `true` could pass the tool an id that matches nothing, and the studio warns
about it.

Your rules then work unchanged. `reply_ticket` for an agent becomes two questions to your PDP, sent as one batch:
`work_on` and `is_open` on that ticket. Because your PDP answers `is_open` for a ticket that exists, the "`not`
alone" trap of step 7 does not arise here.

**What your PDP must answer**

| Laocoon asks | AuthZEN API | Example |
|---|---|---|
| each constraint | Access Evaluation | may user 42 `work_on` ticket `65f1…`? |
| the user's scope, for enums and filters | Resource Search | which tickets may user 42 `work_on`? |
| a name the model wrote ("Bob"), or whether an id exists | Resource Search with the kind's `search` action; the text is in `context.laocoon.reference` | which users may 42 see in the `directory`? |
| who is logged in | Access Evaluation of `identity` with the claimed username and role | is user 42 really `ana`, an `agent`? |

To resolve names, label approval cards and offer the model the allowed values, Laocoon reads the `properties` of
your search results (for example `{"username": "bob", "name": "Bob Agent"}`). AuthZEN does not require them. A PDP
that returns only ids still works: references are then ids only, and the model gets no list of allowed values.

**Operating it.** Your operator sets these:
- `LAOCOON_AUTHZ_SOURCE=authzen`;
- your PDP's address (`LAOCOON_AUTHZEN_PDP`, `https://` only);
- a bearer token your PDP checks (`LAOCOON_AUTHZEN_TOKEN`).

If your PDP is unreachable or answers with an error, every check that needs it is denied at severity medium,
which never locks anyone out, and the identity check fails. The full contract is in
[SPEC §12](SPEC.md#12-authzen-asking-your-own-policy-decision-point).

**Trying it without a PDP of your own.** Laocoon ships a small reference PDP that answers AuthZEN from a JSON file
of objects and relations: no database involved. It is meant for evaluation and as a starting point.

## Changing things later

| Change | What to do |
|---|---|
| You edit the rules (tools, approvals) | validate and save in the studio; your operator deploys |
| You edit `data_model` | regenerate the script. Its diff against the installed one shows exactly what Laocoon will be able to read in addition, or no longer. The DBA reviews and runs it |
| Your application migrates a column the views use (PostgreSQL) | `DROP SCHEMA laocoon CASCADE`, migrate, re-run the script. In between, Laocoon denies the checks it cannot make; nobody is locked out |
| You want to cut Laocoon off | `REVOKE` or `DROP ROLE laocoon`. Every check that needs the database is then denied |

## Common mistakes

| Symptom | Cause | Fix |
|---|---|---|
| The model never uses a tool | the role has no `allow` (or `allow: {role: {}}`) | grant it: `true`, or a constraint |
| "No unique user for 'Maria'" | two users match that tier | refer by username, or put an exact tier first |
| A rule lets through a ticket that does not exist | a `not` path used alone | pair it with a positive path in a list |
| Studio: "user has no relation 'team'" | the path goes the wrong way | follow the declared direction, or declare a `reverse` relation |
| Studio: a view would read `accounts.email` | a sensitive column in `fields` | remove it; rules should not depend on personal data |
| Every write asks, even for admins | that is the default | clear it per role in `approvals.roles` (not possible for locked tools) |
| Calls are denied as "unverifiable" | Laocoon cannot reach the views (network, password, a migration) | run `views check`; fix the connection or re-run the script |
